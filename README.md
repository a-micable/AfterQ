# Cairn

Cairn is a compact C++17 manifest toolkit focused on deterministic parsing,
include resolution, dependency ordering, schema validation, scenario generation,
and fuzz-friendly binary inputs. The repository is intentionally small: each
library unit has one clear responsibility, the command line tool exercises the
same APIs used by tests and fuzzing, and the seed corpus is generated from
normal project code instead of hand-maintained fixtures.

## Project Goals

Cairn exists to make manifest processing boring in the best possible way. A
manifest can define sections, fields, includes, dependencies, schemas, and
conditionals. The parser turns the binary format into typed C++ objects. The
resolver merges included sections while detecting missing references and include
cycles. The evaluator applies schema rules, conditional records, and string
substitution. The dependency sorter provides stable ordering for directed
relationships. The writer mirrors parser expectations so tests and fuzz seeds
can build valid data without duplicating format details.

The design favors explicit data movement over hidden global state. `InternCache`
owns interned strings and keeps handles stable through cache eviction. Parsed
nodes store fields, includes, conditionals, schemas, and dependencies in plain
C++ containers. Runtime errors are surfaced with exceptions, and tests cover the
important failure paths: invalid CRC, missing include, include cycle, dependency
cycle, and schema rejection.

## Repository Layout

`include/cairn/` contains public headers for the library. These headers describe
the project model and the APIs consumed by the command line tool, tests, seed
generator, and fuzz target.

`src/` contains the implementation files. Each `.cpp` file maps closely to a
matching header: parsing, manifest values, include resolution, evaluation,
dependency sorting, manifest writing, CRC calculation, scenario corpus support,
and the CLI entrypoint.

`tests/` contains the native C++ test executable. The test suite builds real
manifests with `ManifestWriter`, parses them with `Parser`, resolves them with
`IncludeResolver`, evaluates them with `Evaluator`, and checks edge cases with
plain assertions and abort-on-failure reporting.

`tools/` contains utilities. `generate_seeds` writes fuzz corpus entries from
curated scenarios. `write_scenario_corpus` is available for expanding or
materializing scenario data when corpus maintenance needs a direct tool.

`fuzz/` contains the libFuzzer entrypoint and the generated corpus directory.
The fuzzer is compiled as C++ and uses the same parser and resolver APIs as
normal program code. Its entry symbol keeps libFuzzer-compatible linkage while
the source remains C++.

`.clusterfuzzlite/` contains ClusterFuzzLite project metadata and the build
script used to compile the fuzzer under sanitizer builds.

## Build Requirements

Cairn builds with a C++17 compiler and `make`. The default compiler is `g++`,
controlled by `CXX`. Warning flags are strict: `-Wall`, `-Werror`, `-Wextra`,
and `-pedantic` are enabled by default. Include paths are supplied through
`CPPFLAGS`, and the project is compiled with optimization and debug information.

The build does not require generated source files to compile. The fuzz corpus is
generated by a tool, but the core library and tests build from checked-in C++
source files.

## Common Commands

Build all normal targets:

```sh
make all
```

Run the test executable:

```sh
make test
```

Regenerate fuzz seeds:

```sh
make seeds
```

Run the full local pipeline:

```sh
make pipeline
```

Remove build outputs:

```sh
make clean
```

## Pipeline

The `pipeline` target is the preferred local verification path. It builds the
CLI, the seed generator, and the test executable; then it runs the test suite;
then it regenerates the fuzz corpus. This gives one command for the normal
quality gate and keeps repository maintenance predictable.

Passing `make pipeline` confirms that the C++ library compiles, the CLI links,
the tests pass, and the scenario corpus generator still works with the current
manifest APIs. It is also a useful guard after changing binary format behavior,
because parser, writer, resolver, evaluator, and corpus generation are exercised
together.

## Manifest Model

A Cairn manifest is organized around named sections. The root section is the
primary entrypoint for parsing and evaluation. Sections may define fields with
typed values, include other sections, declare dependency edges, attach schema
rules, or hold conditional nested manifests.

Fields carry interned keys and typed values. Supported values include strings,
integers, booleans, and floating-point arrays. Values can be converted back to
text for evaluation output and diagnostics.

Includes are resolved by `IncludeResolver`. A registry maps section names to
parsed nodes, and resolution walks include relationships up to a configured
depth. The resolver rejects missing includes and cycles so malformed manifests
do not silently produce partial output.

Schemas are evaluated by `Evaluator`. A schema field records a required key and
expected value type. Validation returns errors when required fields are missing
or values have the wrong type.

Conditionals allow nested manifest data to participate in evaluation when a
condition matches the current evaluated values. This keeps optional content in
the manifest format without forcing all consumers to invent separate side
channels.

Dependencies are represented as edges. `DependencySorter` orders dependency
graphs and rejects cycles. This keeps ordering decisions isolated from parsing
and evaluation.

## Binary Format Safety

The parser reads binary data defensively. CRC checks reject corrupted manifests.
Depth limits protect include resolution from unbounded recursion. Interned
strings keep handles stable even when the cache evicts older entries. Tests use
small cache capacities deliberately to exercise lifetime behavior that might
otherwise only appear under memory pressure.

Fuzzing complements tests by feeding arbitrary bytes into the parser and include
resolver. The fuzzer catches all exceptions because rejected input is expected;
the goal is to find crashes, undefined behavior, and sanitizer failures, not to
make every byte stream valid.

## Testing Strategy

The test suite covers round trips for strings and typed fields, include chains,
cache eviction, include cycles, dependency sorting, dependency cycles, schema
acceptance, schema rejection, conditional evaluation, variable substitution,
CRC rejection, CLI validation, CLI evaluation, missing includes, record parsing,
deep cache eviction during resolution, tiny cache survival, boolean evaluation,
float array text output, custom sections, and scenario corpus resolution.

Tests are intentionally written against public APIs. That makes them useful as
examples for new code and keeps them aligned with actual consumer behavior. When
a public interface changes, tests show which workflows need migration.

## Fuzzing Strategy

The fuzz target constructs a byte vector from libFuzzer input, parses it with
fuzz mode enabled, registers parsed sections, and asks the include resolver to
resolve the parsed root. Any exception is treated as a normal rejection path.
This exercises parser and resolver interaction without requiring input to be a
valid manifest.

The generated corpus supplies valid and near-valid examples so fuzzing starts
from meaningful structure. Corpus entries include minimal manifests, typed
fields, include chains, conditionals, schemas, and conformance scenarios.

## C++ Source Policy

Repository source is maintained as C++ project code. Implementation units use
`.cpp`, public interfaces use `.h`, and the fuzzer source also uses `.cpp`.
ClusterFuzzLite declares the project language as C++ and compiles the fuzzer
with `CXX` under C++17.

The libFuzzer entrypoint keeps `extern "C"` linkage because libFuzzer requires
that exported symbol shape. That linkage requirement does not make the source C;
the file is compiled as C++ and uses C++ containers, exceptions, namespaces, and
library types.

## Development Notes

Prefer changing one subsystem at a time. Parser changes usually require writer,
test, and corpus updates. Resolver changes should include missing include, cycle,
and depth behavior checks. Evaluator changes should include schema and
conditional examples. Dependency sorter changes should include both acyclic and
cyclic graphs.

Keep tests deterministic. The project is small enough that direct assertions are
clearer than a heavy testing framework. When adding new behavior, build the
manifest with `ManifestWriter` unless the test specifically needs malformed
bytes.

Keep the fuzz target broad and cheap. It should continue to exercise real parser
and resolver code without doing slow external work. The fuzzer should not depend
on filesystem state, environment variables, network access, or CLI output.

## Release Readiness Checklist

Before treating a revision as ready, run `make pipeline`. Confirm that no build
artifacts are intended for commit. Confirm that the README matches current
commands and layout. Confirm that fuzz build metadata still points at existing
C++ source files. Confirm that generated corpus entries are produced by the
current seed generator.

## Troubleshooting

If compilation fails, check the first compiler diagnostic. Warnings are errors,
so unused variables, missing includes, narrowing conversions, and portability
issues stop the build.

If tests fail during CLI validation, ensure `make all` built `./cairn` before
running `tests/cairn_tests` directly. The test executable invokes the CLI for
validation and evaluation checks.

If seed generation fails, rebuild `tools/generate_seeds` and inspect scenario
corpus changes. Scenario generation depends on the same manifest writer and
parser assumptions as normal tests.

If ClusterFuzzLite fails to build, check `.clusterfuzzlite/build.sh` for stale
file names and ensure it uses C++17 with the current fuzzer source path.

## Maintenance Philosophy

Cairn is easiest to maintain when the binary format, writer, parser, evaluator,
resolver, sorter, tests, and fuzz seeds move together. Small changes are welcome
when they preserve that alignment. Large changes should include pipeline updates
so future contributors can verify the same behavior with one command.
